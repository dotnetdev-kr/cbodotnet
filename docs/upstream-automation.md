# Upstream SDK automation

The [upstream workflow](../.github/workflows/upstream-sdk.yml) checks official .NET release metadata daily at 03:23 UTC and can also be dispatched manually. It tracks stable SDKs from .NET Core 3.0/3.1 and .NET 5 onward, including channels marked end of life. It reads every channel document, considers both `sdk` and `sdks`, and summarizes the latest published SDK in each feature band. In the admitted automatic adapter's band, every stable SDK newer than the baseline enters a persistent retry queue until its public release exists. Missed polling intervals do not skip intermediate updates. New stable major versions are discovered through the official channel index.

Each check preserves its complete status table in the workflow summary and a 30-day plan artifact. Public releases named `sdk-VERSION` provide the durable completion state. An existing completed release is skipped; failed builds without a release draft are retried. Runs are serialized, publication verifies existing assets rather than replacing them, and the next check retries a version whose public source tag has not appeared yet. No support lifecycle filter suppresses discovery or removes an existing community release.

## Automatic build admission

The automatic adapters derive from the qualified **.NET 8.0.133 (1xx), .NET 9.0.123 (1xx) and .NET 10.0.403 (4xx)** pipelines and admit later stable SDKs in those feature bands. Each new SDK must pass the complete two-architecture build and verification gates before it is qualified or released. The .NET 8 adapter retains its source-build construction, while .NET 9 and 10 retain their ordinary VMR construction and corresponding input provenance. Other pinned families remain available through their established manual matrix workflows. A metadata entry in another feature band or major version is recorded as `pending-adapter`; an absent exact public VMR release tag is recorded as `pending-source`, including newer bands. Neither state is reported as a completed build. Tracking all channels does not establish that an arbitrary future source layout already builds successfully.

For an admitted version, the workflow resolves and peels its exact `dotnet/dotnet` release tag to a full commit. It derives bootstrap and component versions from that commit's source manifests; .NET 10 also binds the reused shared SDK package and corresponding shared VMR commit. The runtime version must match the official SDK release metadata. There is no fallback to another SDK's source tag or an upstream binary product SDK.

The .NET 8 and 9 adapters derive changed bootstrap SDKs from the immutable source configuration and require official SDK release metadata SHA-512 checksums for both Linux architectures. The .NET 8 source-build adapter also binds the exact versioned source-pinned prebuilt source-built archive. For a new archive without a separately published checksum, discovery records its observed HTTPS bytes, SHA-256 and SHA-512; each native generation and the independent publication generation downloads it again and requires equality. This is independently repeated observation of the exact upstream URI, not a claim of a detached publisher signature. Known baseline inputs must still match their retained qualified digest pins. An unavailable or incompatible bootstrap input is reported as `pending-bootstrap` and cannot silently reuse an earlier version's bytes.

Before running upstream code, a read-only source inspection requires the selected family's sysroot producers, patch inputs and executed test closure to remain unchanged. The .NET 9 ordinary adapter freezes UnifiedBuild, TestUtilities and scenarios plus their root build/import wiring; unexecuted source-only SmokeTests remain in the authentic source payload without an execution claim. The full existing test counters, package identities and allowed skips remain mandatory. A changed compatibility input fails admission and retains diagnostics; it requires a qualified adapter update. Source inspection does not execute upstream build scripts.

The workflow clones the trusted orchestration commit into a new sandbox and changes only the explicit adapter files and two generated SDK profiles. It replaces version and immutable source pins, regenerates .NET 10's complete corresponding shared source Git attribute audit, and creates a deterministic local Git commit. This generated commit is an effective build input, with the actual scheduled workflow commit retained as its parent. The workflow does not push generated commits to `main`. The attestation binds both commits, the candidate SHA-256, upstream compatibility inventory and any corresponding source attribute audit.

Both native GitHub runners independently derive the same adapter, then perform the complete existing preparation, build, clean-source binary scan, original upstream tests, actual used-source packaging, three Linux user-space verifications and final evidence validation. Public architecture names are `aarch64` and `x64`; official .NET RIDs inside SDKs and provenance remain `linux-arm64` and `linux-x64`. The existing family-specific glibc ceilings, original package inventories and framework origin statements remain in force. Reused upstream shared framework binaries are accompanied by their exact corresponding source checkout; ordinary builds do not claim reused frameworks were rebuilt locally. The .NET 8 and 9 hosted workers require the existing 90-GiB planning capacity gate, and .NET 10 retains its 30-GiB gate.

## Publication and recovery

Build jobs have read-only repository permissions and no persisted checkout credentials. The separate publication job independently derives its verifier from the original trusted orchestration commit and candidate, verifies both exact-run transport checksums, and reruns the complete portable source and SDK evidence gates. It compares both build attestations with its independently generated attestation before passing the pair to the release publisher. It never runs verifier code obtained from a downloaded artifact.

Only a successful `aarch64` and `x64` pair is published. Releases include both binaries, the actual source and evidence payloads, checksums, immutable build origins and adapter provenance. A failed architecture, source inspection, source match, native check or release verification prevents publication. A completed release is the idempotency key; the publisher can verify/resume an incomplete draft with the same staged files. A draft left by interrupted publication is reported as `pending-publication-recovery` and prevents a new build from overwriting its original run-bound assets. Recovery must use that draft's exact qualified original files. A manually rerun full workflow attempt has a new attempt identity throughout its evidence and transport names.

The daily check retries missing sources and failed candidates. A compatibility failure needs a reviewed adapter change rather than a weaker check. The current per-run candidate limit is one SDK version, configured in [upstream-policy.json](../profiles/upstream-policy.json). Successful publication dispatches the Pages workflow so its minimal download index reflects the public releases. If the index deployment fails after publication, rerunning Pages repairs the index without rebuilding or republishing the SDK.

Metadata format and source organization references: [official release metadata documentation](https://github.com/dotnet/core/blob/main/release-notes/schemas/README.md), [VMR build documentation](https://github.com/dotnet/dotnet#building), and [VMR branching and tagging](https://github.com/dotnet/dotnet/blob/main/docs/VMR-Upstream-Downstream.md#branching-and-tagging).

## Qualifying the generated adapter

Dispatch the upstream workflow with `qualify_baseline=true` and `qualify_target=net10`, `net9` or `net8` to exercise the selected generated adapter using its exact admitted source pins. This mode performs both complete native build pipelines and the independent publication-job source verification and staging gates. It retains an `upstream-qualified-staging-VERSION-RUN-ATTEMPT` artifact and deliberately skips public release publication and Pages dispatch. Qualification runs have a separate concurrency lane for each family; production discovery and publication retain their shared serialized lane. Scheduled runs leave qualification disabled. The CLI equivalent is `upstream-sdk.py discover --qualify-baseline --qualify-target net8` (or the other selected family); sandbox generation requires the explicit `--allow-baseline` flag. A successful baseline qualification establishes the orchestration path, while each future source revision still needs its own complete qualification.

The generated .NET 10 baseline completed both native architectures and independent source verification and release staging in [qualification run 41318630621](https://github.com/dotnetdev-kr/cbodotnet/actions/runs/41318630621). Its trusted workflow commit was `4a5043f41e74131d7a312532f29ad9fbb4166129`, and all three independent derivations produced `e8a3bbc831749bb18cf868c22518215846bb3b5c`. Each architecture's actual source payload contained 264,511 files. The independently qualified staging artifact is `13090003420`; this qualification did not change a public release. The new .NET 8 and 9 generated adapters still require their own complete hosted qualification; their original pinned native pipelines have already passed.
