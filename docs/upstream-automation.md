# Upstream SDK automation

The [upstream workflow](../.github/workflows/upstream-sdk.yml) checks official .NET release metadata daily at 03:23 UTC and can also be dispatched manually. It tracks stable SDKs from .NET Core 3.0/3.1 and .NET 5 onward, including channels marked end of life. It reads every channel document, considers both `sdk` and `sdks`, and summarizes the latest published SDK in each feature band. In the admitted automatic adapter's band, every stable SDK newer than the baseline enters a persistent retry queue until its public release exists. Missed polling intervals do not skip intermediate updates. New stable major versions are discovered through the official channel index.

Each check preserves its complete status table in the workflow summary and a 30-day plan artifact. Public releases named `sdk-VERSION` provide the durable completion state. An existing completed release is skipped; failed builds without a release draft are retried. Runs are serialized, publication verifies existing assets rather than replacing them, and the next check retries a version whose public source tag has not appeared yet. No support lifecycle filter suppresses discovery or removes an existing community release.

## Automatic build admission

The automatic adapter derives from the qualified .NET 10.0.403 pipeline and admits **new .NET 10.0.4xx SDK updates after 10.0.403**. Each new SDK must pass the complete two-architecture build and verification gates before it is qualified or released. These versions use the project's existing portable ordinary VMR build. The other pinned families remain available through their established manual matrix workflows. A metadata entry in another feature band or major version is recorded as `pending-adapter`; an absent exact VMR release tag is recorded as `pending-source`. Neither state is reported as a completed build. Tracking all channels does not establish that an arbitrary future source layout already builds successfully.

For an admitted version, the workflow resolves and peels its exact `dotnet/dotnet` release tag to a full commit. It derives bootstrap SDK, shared SDK package, reused runtime version and corresponding shared VMR commit from that commit's `global.json` and `eng/Version.Details.xml`. The runtime version must match the official SDK release metadata. There is no fallback to another SDK's source tag or an upstream binary SDK.

Before running upstream code, a read-only source inspection requires the original sysroot producers and scenario report synchronization patch input to remain byte identical. The original upstream test source, project definitions, targets and directory build properties must remain unchanged. The full existing test counters and allowed skips remain mandatory. A changed compatibility input fails admission and retains diagnostics; it requires a qualified adapter update. Source inspection does not execute upstream build scripts.

The workflow clones the trusted orchestration commit into a new sandbox and changes only the explicit adapter files and two generated SDK profiles. It replaces version and immutable source pins, regenerates the complete corresponding shared source Git attribute audit, and creates a deterministic local Git commit. This generated commit is an effective build input, with the actual scheduled workflow commit retained as its parent. The workflow does not push generated commits to `main`. The attestation binds both commits, the candidate SHA-256, upstream compatibility inventory and shared source attribute audit.

Both native GitHub runners independently derive the same adapter, then perform the complete existing preparation, build, clean-source binary scan, original upstream tests, actual used-source packaging, three Linux user-space verifications and final evidence validation. Public architecture names are `aarch64` and `x64`; official .NET RIDs inside SDKs and provenance remain `linux-arm64` and `linux-x64`. The existing glibc ceiling and framework origin statements remain in force. Reused upstream shared framework binaries are accompanied by their exact corresponding source checkout; this ordinary build does not claim those frameworks were rebuilt locally.

## Publication and recovery

Build jobs have read-only repository permissions and no persisted checkout credentials. The separate publication job independently derives its verifier from the original trusted orchestration commit and candidate, verifies both exact-run transport checksums, and reruns the complete portable source and SDK evidence gates. It compares both build attestations with its independently generated attestation before passing the pair to the release publisher. It never runs verifier code obtained from a downloaded artifact.

Only a successful `aarch64` and `x64` pair is published. Releases include both binaries, the actual source and evidence payloads, checksums, immutable build origins and adapter provenance. A failed architecture, source inspection, source match, native check or release verification prevents publication. A completed release is the idempotency key; the publisher can verify/resume an incomplete draft with the same staged files. A draft left by interrupted publication is reported as `pending-publication-recovery` and prevents a new build from overwriting its original run-bound assets. Recovery must use that draft's exact qualified original files. A manually rerun full workflow attempt has a new attempt identity throughout its evidence and transport names.

The daily check retries missing sources and failed candidates. A compatibility failure needs a reviewed adapter change rather than a weaker check. The current per-run candidate limit is one SDK version, configured in [upstream-policy.json](../profiles/upstream-policy.json). Successful publication dispatches the Pages workflow so its minimal download index reflects the public releases. If the index deployment fails after publication, rerunning Pages repairs the index without rebuilding or republishing the SDK.

Metadata format and source organization references: [official release metadata documentation](https://github.com/dotnet/core/blob/main/release-notes/schemas/README.md), [VMR build documentation](https://github.com/dotnet/dotnet#building), and [VMR branching and tagging](https://github.com/dotnet/dotnet/blob/main/docs/VMR-Upstream-Downstream.md#branching-and-tagging).

## Qualifying the generated adapter

Dispatch the upstream workflow with `qualify_baseline=true` to exercise the generated adapter using the exact admitted 10.0.403 source pins. This mode performs both complete native build pipelines and the independent publication-job source verification and staging gates. It retains an `upstream-qualified-staging-VERSION-RUN-ATTEMPT` artifact and deliberately skips public release publication and Pages dispatch. Scheduled runs leave this option disabled. The CLI equivalent for discovery is `upstream-sdk.py discover --qualify-baseline`; sandbox generation requires the explicit `--allow-baseline` flag. A successful baseline qualification establishes the orchestration path, while each future source revision still needs its own complete qualification.
