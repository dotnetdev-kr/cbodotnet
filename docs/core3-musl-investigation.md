Issue [#35](https://github.com/dotnetdev-kr/cbodotnet/issues/35) now has a demonstrated native ARM64 musl bootstrap and dependency adaptation route. **Go for producer implementation and two-CPU qualification; no release admission yet.** The remaining work is to compile the selected SDK/core-sdk source graph and qualify its actual output on native x64 and ARM64. The private imported managed SDK used below is bootstrap input, not a replacement for that source build.

The official [3.1 metadata](https://builds.dotnet.microsoft.com/dotnet/release-metadata/3.1/releases.json) has no ARM64 musl SDK at 3.1.426, but it does publish ARM64 musl runtime/ASP.NET archives at 3.1.32 and the 3.1.422 bootstrap runtime at 3.1.28. The exact [ARM64 musl apphost package 3.1.32](https://www.nuget.org/packages/Microsoft.NETCore.App.Host.linux-musl-arm64/3.1.32) also exists. Its official NuGet catalog SHA512 matches the retained bytes; its nuspec identifies core-setup `f94bb2c3ff432dcc4a6229eca2f978197bf06150`, already retained as complete source. The package includes MIT licensing, third-party notices and a signature envelope; this investigation does not substitute envelope presence for final publisher-signature qualification.

The [3.0 metadata](https://builds.dotnet.microsoft.com/dotnet/release-metadata/3.0/releases.json) omits ARM64 musl archives, but the official NuGet catalog publishes ARM64 musl runtime, apphost, DotNetHost, DotNetHostResolver, DotNetHostPolicy and ASP.NET packages at **both 3.0.0 and 3.0.3**. Original catalog SHA512 values match the retained native components. Actual composition of the 3.0.0 musl runtime/host/resolver with imported SDK3.0.100 PE/data runs MSBuild16.3, offline SDK restore/build/execution and the managed crypto/full-ICU/system-trust probes. The private framework dependency JSON is adapted from original SDK metadata with its RID change recorded; a source producer must generate its own metadata. The runtime pack's foreign `runtimes/x64_arm64/native/libclrjit.so` is explicitly excluded, hashed and classified. No foreign cross-JIT executes.

The fixed [experimental profile](../profiles/experimental/core3-musl.json) pins both complete selected source graphs for CLR, CoreFX, core-setup, ASP.NET, SDK and core-sdk, plus the source-build roots. All 14 original archives and the complete runtime6 donor archive are retained with hashes and license/notice inventories. The local source review records exact file hashes and lines for ARM64 Alpine toolchain support, ASP.NET musl ARM64 identifiers, root/component bootstrap versions, and the old source-build properties that rewrite portable RIDs to `linux-*`. The last property behavior must be corrected in a genuine producer; passing a root RID alone is insufficient.

Actual probes ran in native AArch64 WSL with SDK-free Alpine 3.24.4, Clang20, CMake4.2, musl1.2.6, OpenSSL3.5.9, full ICU78.1 and stock lttng-ust2.14. They ran as user10001 with dropped capabilities and no-new-privileges. These are local rootful Podman diagnostics, not GitHub Actions qualification. Final qualification still requires matching native Docker runners with the normal security policies.

The normal SDK apphost build restores exactly `Microsoft.NETCore.App.Host.linux-musl-arm64` **3.1.32** from the retained local feed, as recorded in `project.assets.json`. The separate consumer uses only the official musl3.1.32 runtime/ASP.NET framework plus the two locally rebuilt native replacements and compiled test applications. It does not mount an expanded private SDK. Its complete runtime and apphost ELF closures pass. Core3.0's clean component bootstrap and closure also pass in this same minimal runtime image; a separate Core3.0 apphost/ASP.NET consumer remains unqualified.

The crypto adaptation is a small [two-file patch](../patches/core3-musl/0001-branch-native-openssl3.patch): use upstream runtime6 OID parsing rather than the removed OpenSSL error-function field, and preserve the old managed X509 error ABI. It deliberately links the current branch's OpenSSL3. The [two-line PAL patch](../patches/core3-musl/0002-clang20-typed-null.patch) preserves the original pointer values. Neither adaptation supplies an EOL OpenSSL companion. Before release, managed tests must demonstrate fail-closed behavior for an untrusted self-signed certificate, expired certificate, wrong host name and invalid CA chain. The positive system-trust connection and native error-code roundtrip do not constitute that security qualification.

`COMPlus_ReadyToRun=0` applies only to the imported private bootstrap, so glibc-origin native ReadyToRun sections are not executed. It is not a policy for the final SDK: the source-built product must retain and qualify its normal optimizations and native apphost behavior.

The complete ELF audit uses `musl_archive.audit_elf`. `GLIBC_2.0` attached specifically to `libgcc_s.so.1` is GCC's unwind ABI namespace: the actual Alpine libgcc15.2.0-r5 defines it and remains musl-linked. The existing provider-specific rule is reused. No general GLIBC version exception, glibc provider, gcompat, loader change or soname link is introduced. The worker closure also exposes **two additional stock runtime package roots**, `libcurl=8.23.0-r0` and `libintl=1.0-r0`, beyond the existing 13 roots; their dependency closure must be declared in a Core3 runtime policy. Compiler/development packages in a probe worker must not mask consumer dependencies.

The separate [consumer recipe](../containers/core3-musl-consumer-probe.Containerfile) declares those two package roots explicitly. The [consumer probe](../scripts/core3-musl-consumer-probe.py) records every actual native provider's version, origin, license, checksum and dependency declarations from the frozen stock-signed APK indexes. `libcurl` comes from Alpine's `curl` origin/license `curl`; `libintl` comes from `gettext` under `LGPL-2.1-or-later`. No private compatibility provider is involved. The existing SDK10 runtime policy is not changed.

The reusable helpers are [source/native/trace probes](../scripts/core3-musl-probe.py), [private bootstrap probe](../scripts/core3-musl-bootstrap-probe.py), and an [SDK-free worker recipe](../containers/core3-musl-probe.Containerfile). The worker takes the matching Alpine base/index pins from the existing musl profile and authenticated index snapshots. It retains its APK transaction. From a new input directory:

```sh
python3 scripts/core3-musl-probe.py acquire --inputs-dir "$PWD/.build/core3-inputs" --bootstrap --bootstrap-core30
python3 scripts/core3-musl-probe.py review --inputs-dir "$PWD/.build/core3-inputs" --output-dir "$PWD/.build/core3-review"
```

Inside the matching non-root worker, with the project/inputs mounted read-only and separate writable report mounts, run `native --arch aarch64 --candidate-port`, then `trace --arch aarch64`. Pass the successful native and trace evidence directories to `core3-musl-bootstrap-probe.py --family core31` or `--family core30`, with `--native-evidence ... --trace-evidence ... --tls`. All commands require new report directories. `native` without `--candidate-port` retains the original failure/control. A probe's process completion is never SDK admission; inspect target exit codes and the separate closure report.

The machine-readable [evidence summary](core3-musl-investigation.json) identifies the actual retained reports and hashes. Complete source archives, original vendor inputs, generated trace source, compiler logs, ELF closure, excluded SDK ELF inventory, patch receipts and managed probe source remain under `.build/core3-musl-investigation/`. These local artifacts are not published or admitted into release catalogs.

Producer work still must build the exact SDK/core-sdk source, preserve component/bootstrapping provenance, use the genuine musl apphost and ASP.NET paths, and complete SDK-free non-root/offline apphost/HTTP/crypto/full-ICU/system-trust qualification on both CPUs. Consumer archives, APK lifecycle/signing/indexes, OCI tags, anonymous verification and installer admission follow only after that qualification. Existing glibc releases and SDK10 musl admission are unchanged. Core3.0 and Core3.1 remain upstream EOL; this prototype adds no security-maintenance or Microsoft-support claim. Workloads and NativeAOT remain unqualified.
