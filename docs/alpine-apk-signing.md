# Alpine APK signing and repository design

This is the reviewed candidate design for issue #24. A generated APK, an upstream
SDK fixture, or a passing packaging test does not authorize publication. Native
musl producer admission, both CPU consumer receipts, the approved permanent APK
key, protected publication, and anonymous verification are separate gates.

Alpine's [current stable branch](https://alpinelinux.org/releases/) is 3.24;
3.24.4 was released on November 5, 2026. The implementation pins its actual
`linux/amd64` and `linux/arm64` official image manifests, not a floating tag.
The observed repository baseline has `apk-tools 3.0.9-r0` and
`abuild 3.17.0-r0`. These observations must be checked by authenticated APK
transactions in each native job; mutable CDN metadata is not a qualification.

The [abuild 3.17 implementation](https://github.com/alpinelinux/abuild/blob/3.17.0/abuild.in)
still creates **v2 tar/gzip APK packages and APKINDEX.tar.gz indexes**.
The apk-tools major version alone does not select an ADB/v3 package format.
Its [signing implementation](https://github.com/alpinelinux/abuild/blob/3.17.0/abuild-sign.in)
defaults to `RSA`, meaning SHA-1. Every project package/control and index uses
the explicit **RSA256** type: RSA-4096 with SHA-256. `sigtype=RSA256` is exported
for abuild's package signing; the index call also passes `-t RSA256`.
The actual signature member must be `.SIGN.RSA256.<public-key-file-name>`.
The [apk v2 verifier](https://github.com/alpinelinux/apk-tools/blob/v3.0.8/src/extract_v2.c)
recognizes this signature type. Native consumers must also use `apk verify` and
real signature-enforced transactions; no `--allow-untrusted` is permitted.

## Approved permanent trust identity

The owner explicitly approved creating and using the dedicated APK key on
November 7, 2026. Its private key was stored in the protected environment
secret; the local temporary copy was deleted. No permanent key is generated by
the packaging scripts. The existing project
Ed25519 OpenPGP key remains the release-manifest signer. It is not an APK trust
key. The separate identity is:

| Setting | Value |
| --- | --- |
| Key | Dedicated RSA-4096 key; PEM private key, PEM SubjectPublicKeyInfo public key |
| Package/index signature | RSA256 (SHA-256, OpenSSL RSA PKCS#1 v1.5 signing) |
| Public filename | `cbodotnet-apk-2026.rsa.pub` |
| Checked-in public path | [`releases/cbodotnet-apk-2026.rsa.pub`](../releases/cbodotnet-apk-2026.rsa.pub) |
| Protected environment secret | `APK_SIGNING_KEY` (multiline PEM; never a repository-wide secret) |
| Environment | Existing `downstream-release`, restricted to the reviewed main-branch publication workflow |
| Consuming workflow | `.github/workflows/musl-release.yml`, protected APK signing/promotion job only |
| Fingerprint | SHA-256 of DER SubjectPublicKeyInfo, plus SHA-256 of the exact published PEM file |
| Created | `2026-11-07T06:46:45Z` |
| Rotation cutoff | `2028-11-07T06:46:45Z`; enforced by publisher policy before signing |

The SHA-256 fingerprint of the public key's DER SubjectPublicKeyInfo is
`784ae05c3339c239f715cb0b849dead89e6a1b787a8126c738d6997227a63e20`.
The SHA-256 of the exact published PEM file is
`d464a8e7c173c1a86ad65f92abb1d56fd1f362dbcaf30b4b3929355bc6a49c2d`.
The reviewed [`musl-signing-policy.json`](../releases/musl-signing-policy.json)
binds both values, the filename, secret, environment, workflow, creation date
and publisher cutoff.

Raw RSA APK keys have **no native expiry date or revocation certificate**.
The two-year cutoff is a project signing policy, not a client-enforced expiry.
Do not describe it as equivalent to OpenPGP expiry. The approved public key,
fingerprints, creation/cutoff timestamps, and allowed workflow are frozen in
reviewed policy. A private key is loaded only into a
temporary directory with owner-only permissions, is never put in an artifact,
and is removed in an unconditional cleanup step. Untrusted build jobs cannot
read that environment or private key.

Prepare rotation before the cutoff: publish the next public key and its exact
fingerprints through the existing OpenPGP-authenticated project channel; let
clients install the new key; publish new immutable package/repository revisions
under it; retain old releases for explicit historical verification. Do not
overwrite old signatures or silently replace a public key under the same
filename. Compromise requires stopping publication and asking users to remove
the compromised key from `/etc/apk/keys`; raw APK trust has no automatic remote
revocation mechanism. No untested claim of transparent dual signatures is made.

## Package ownership and immutable delivery

`cbodotnet-sdk-X.Y` owns `/opt/cbodotnet/X.Y` and
`/usr/bin/cbodotnet-X.Y`. A separate `cbodotnet-host` (`noarch`) owns
`/usr/bin/cbodotnet`, whose existing shell selector chooses the highest usable
installed major/minor. No hooks, alternatives, `replaces=dotnet-host`, or
`provides=dotnet-host` are created. `/usr/bin/dotnet` remains owned by Alpine's
independent official `dotnet-host` package. Removing one Community SDK leaves
the common selector available for remaining SDKs.

The APKBUILD preserves qualified SDK files: it disables stripping, debug splits,
and dependency/provider inference over embedded SDK assets. Reviewed stock
dependencies are explicit and proved independently in a clean consumer. The
local SDK aggregate `LicenseRef-Dotnet-SDK-ThirdParty` names its retained
`LICENSE.txt` and `ThirdPartyNotices.txt`; it does not relabel all components MIT.
The SPDX whitelist exception applies to this local LicenseRef. Build/source,
recipe, original notices, exact package SHA-256s, index, key identity, source
manifest, and native reports must be bound by the OpenPGP-signed release manifest.
Alpine's aports FHS check forbids `/opt`; this independent third-party package
therefore disables that aports check while its own inventory strictly permits
only the reviewed `/opt/cbodotnet/X.Y`, Community launcher and documentation
paths. This is not an assertion of official aports policy compliance.

The two-platform signed distribution record uses
`distribution-musl-apk-sdk-V-rN`. Each CPU's flat repository has a distinct
immutable release tag `musl-apk-repo-V-alpine324-{x64|aarch64}-rN` containing
canonical `cbodotnet-sdk-X.Y-V-rN.apk`, `cbodotnet-host-1.0.0-r1.apk`, and
`APKINDEX.tar.gz` filenames. APK architecture is in the index/package metadata.
With apk-tools 3, an explicit [`ndx` repository URL](https://github.com/alpinelinux/apk-tools/blob/v3.0.8/doc/apk-repositories.5.scd)
points directly at `.../APKINDEX.tar.gz`, and packages resolve beside it. This
avoids copying large SDK packages into GitHub Pages or inventing unsupported
package URLs. Anonymous HTTPS downloads and real installs must prove this route
before it is advertised.

The Alpine OCI variant keeps a distinct `V-alpine324-musl-rN` tag and a signed
two-platform index. Its pinned base and qualified SDK are unchanged by packaging.
`cbodotnet-X.Y`, `cbodotnet`, and `dotnet` all select the Community CLI inside
the image. The default image user is `app` (UID/GID 1654).

## Required native acceptance evidence

Use SDK-free, digest-pinned Alpine 3.24.4 consumers on each matching native CPU.
Record exact installed dependency versions, repository/index hashes and trusted
key filenames. Exercise install, reinstall, upgrade, explicit rollback, removal,
common-host retention/selection, and official `/usr/bin/dotnet` ownership before
and after. Run offline console, apphost, ASP.NET HTTP, TLS/crypto, full ICU and
timezone probes as a non-root user. Audit all payload ELF files and distinguish
documented non-host target assets. `gcompat`, loader aliases and invariant-only
globalization cannot qualify a musl payload.

Verify both signed packages and index positively. In isolated consumer roots,
reject a changed package/control, changed data payload, changed index, missing
key, and a different RSA key under the expected filename. An index checksum
failure and an untrusted signature failure are recorded separately. Install the
actual anonymous release bytes after promotion, then repeat the same native
checks. Ephemeral test keys and upstream SDK fixtures are always labelled as
fixtures and never entered into production qualification catalogs.

NativeAOT, optional workloads, cbodotnetup admission (#30), other SDK versions,
and official aports admission require their own evidence and are not implied by
an APK assembly pass.
